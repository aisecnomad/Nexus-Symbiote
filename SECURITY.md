# Security policy

Nexus SymBiote is alpha security tooling. Inventory, signature verification, and policy decisions have different meanings. A successful scan or low risk score does not establish that an agent, model, dataset, or tool is benign.

## Reporting a vulnerability

Report security-sensitive defects through the repository's **Security > Report a vulnerability** feature ([open a private report](https://github.com/Hunzee-VC/Nexus-Symbiote/security/advisories/new)) when available. If private reporting is unavailable, contact the repository owner through their GitHub profile and request a private reporting channel. Do not put credentials, private BOMs, exploit details, or customer data in a public issue.

Include the affected commit or distribution version, platform and Python version, reproduction steps with synthetic inputs, expected and observed behavior, and the trust boundary crossed. Keep real credentials and sensitive agent context out of reproduction artifacts.

The project does not promise response or remediation deadlines. Maintainers should acknowledge a report, agree on a disclosure plan with the reporter, and publish an advisory with affected and fixed versions when appropriate.

## Supported versions

Only the latest reviewed alpha revision is developed. There is no long-term support commitment or established production support window. Confirm release provenance and the matching source revision before installing a published distribution.

## Imported discovery evidence

Treat ShadowScan reports, CycloneDX imports, A2A cards, IDE settings, and extension manifests as untrusted inputs. A discovery record does not grant authority or authenticate the discovered endpoint. Verify the expected subject, signer, tenant, time, and policy before upgrading a claim. Never grant deployment or publication credentials to the import job merely to parse a report.

To require that a merged inventory's ShadowScan evidence comes from a signed report, name the report in an operator signature policy kept outside the checkout and pass it to `validate --project` or `risk --project` ([require a signed report in CI](docs/shadowscan-integration.md#require-a-signed-report-in-ci)). Setting `validate.require_discovery_signature: true` in the project policy also turns the check on. The content digest that `diff` compares detects drift; it does not authenticate a report.

## Security boundaries

Static collection must not execute project modules, model loaders, repository hooks, or MCP launch commands. Treat repositories, model files, tool metadata, registry records, and imported BOMs as hostile input. Run scans with read-only access and without deployment or publication credentials.

Confined file operations and pinned stdio launchers require POSIX descriptor-relative and no-follow primitives. Unsupported platforms fail closed rather than weakening those checks. Hard links are regular files: a hard-linked file inside the scanned root is read and hashed like any other, so an inventory can describe an inode that also has a name outside the root. Run static collection with the content author's privileges rather than as root, on hosts with `fs.protected_hardlinks=1`, and extract untrusted archives with a tool that refuses link targets outside the destination (GNU tar, or Python `tarfile` with `filter='data'`). The configured hosted matrix targets Ubuntu with Python 3.11 through 3.14; it does not qualify macOS or Windows support.

`verify-live` is an explicit execution operation. Its operator-owned launch policy must be outside the scanned project and binds exact server references to independently obtained executable SHA-256 pins. It stages the approved bytes privately, passes no project arguments, clears inherited environment variables, uses a private working directory and terminates the process group after bounded protocol collection. It invokes no tools. Launcher pins do not authenticate the OS, interpreter, linked libraries or other host dependencies. Execute launchers in an externally isolated worker with resource limits and restricted filesystem, identity and network access. `--record` emits a separate unsigned candidate, not an approval or admission decision; incomplete observations and missing tools fail closed.

A signature proves that authorized key material signed particular bytes under the verifier's policy. It does not prove that the content is accurate or safe. A matching tool descriptor cannot prove that the backend behaves as declared. Enforcement integrations govern only calls actually mediated by those integrations.

Agent inventories can expose infrastructure, permissions, endpoints, and instruction fingerprints. Restrict access to exported evidence and review its contents before sharing it. Keep raw credentials out of BOMs, logs, and issue reports.

## Coverage changes after 0.1.0

When found within the scanned scope, nested instruction files, GitHub and
Cursor instruction directories, Claude subagent definitions, unsupported skill
package files, partially inventoried IDE settings and unsupported MCP config or
server forms produce coverage gaps. Default-excluded directories nested under
skill or command packages also produce gaps. A default gate fails with these
gaps; `--report-only` permits inspection of the partial inventory. Static source
hints are conservative and cannot identify every possible agent declaration,
and paths outside the collection scope remain unobserved. A passing gate still
does not establish global completeness.

## Discovery binding and resource limits after 0.1.0

An operator signature policy can require a separately signed discovery context
that binds the report digest to the expected repository, revision, scope, producer
version and maximum age; see [the integration guide](docs/shadowscan-integration.md).
The context is an authenticated producer claim, not proof of collection accuracy.
The producer can sign misleading claims, and a report can be replayed within the
allowed age. Without this context, the 0.1.0 replay limitation below still applies.

TypeScript source analysis now limits AST depth and per-file analysis time, and
the JavaScript comment hint uses a linear scan. Limits fail collection rather
than establish complete coverage. These are not a whole-job CPU or wall-clock
budget: use an external timeout and resource limits for untrusted inputs.

## Known limitations in 0.1.0

The pre-publication review of 0.1.0 confirmed these gaps. When a scan meets one of the detection gaps below, it still reports complete coverage, and neither `validate`, `risk` nor `diff --fail-on-alert` can flag what the inventory does not record, so review changes to those files by other means until a later release covers them.

- **Claude Code settings.** From `.claude/settings.json` and `.claude/settings.local.json` the inventory records the permission mode (`defaultMode`) and whether the allow list contains a blanket grant (`Bash`, `Edit`, `Write`, their `(*)` forms, or `*`). It records nothing else from those files and no digest of them: not `hooks`, `permissions.deny` or `ask`, narrower `allow` entries, `apiKeyHelper`, `permissions.additionalDirectories`, `enableAllProjectMcpServers` or `enabledMcpjsonServers`. Removing a deny rule, adding a hook command, or adding a second blanket grant when one is already present produces no change and no alert. For other IDE agents the inventory records which marker files exist and, only from an `agent.permissionMode` key in `.cursor/settings.json`, `.windsurf/settings.json`, `.cline/settings.json` or `.codex/config.json`, a permission mode. Codex `config.toml` settings such as `approval_policy` and `sandbox_mode` are not read, and no mode is read for Copilot.
- **Instruction files outside the fixed paths.** The `prompt` collector reads instruction files only at the fixed paths the README lists, relative to the project root. Nested `CLAUDE.md` or `AGENTS.md` files in subdirectories, `.github/instructions/`, `.github/prompts/` and `.cursor/rules/` are neither inventoried nor checked for hidden characters.
- **Skills, commands and subagents.** In `.claude/skills`, `.claude/commands` and `skills`, only `.md`, `.txt`, `.yaml`, `.yml` and `.json` files are inventoried, by digest. Bundled scripts such as `.sh`, `.py` or `.js` files are skipped without a coverage gap. Hidden-character detection runs on instruction files such as `CLAUDE.md` and `AGENTS.md`, not on skill and command files. Subagent definitions in `.claude/agents/` are not collected.
- **Hidden-character detection uses a fixed list.** It reports U+200B to U+200D, U+2060 and U+00AD, the bidi embedding, override and isolate controls U+202A to U+202E and U+2066 to U+2069, and the tag characters U+E0001 to U+E007F. Other invisible or format characters, such as U+FEFF, the LRM, RLM and ALM marks, U+180E, the invisible operators U+2061 to U+2064, variation selectors and U+3164, produce no finding.
- **Default exclusions match by name.** Any path component named `.git`, `node_modules`, `__pycache__`, `.venv` or `venv` is skipped everywhere, including inside agent-configuration directories, so `.claude/skills/venv/SKILL.md` is not inventoried. The patterns appear under `exclusions` in the BOM but are not reported as a coverage gap, and standard exports keep coverage `unknown` for them, as bare names or as `**/name`. Any other exclusion entry, including another spelling such as `./node_modules`, makes coverage `incomplete`.
- **Standard fields carry coverage only coarsely.** CycloneDX `compositions` and SPDX relationship `completeness` say only `incomplete`, or `unknown` (`noAssertion` in SPDX); no export says `complete`. Which collectors ran, what failed and what was excluded are only in the native extension. An SPDX export with no native-edge relationships states its coverage only in the free-text document `comment`; license relationships carry no `completeness`. cyclonedx-python-lib 11.12.0 drops `compositions` when it reserializes a BOM. That removes an `incomplete` warning, and SymBiote recovery then rejects the document; dropping an `unknown` composition removes no assertion, so that document still recovers. The CycloneDX `nexus-symbiote:dependency:relationship` property is an extension, not a standalone edge source: it marks a conditional edge only with `"conditional": true`, and in CycloneDX the condition text, like the edge's assurance level, is only in the embedded native document.
- **Exports from earlier builds may not recover.** CycloneDX and SPDX exports written by earlier builds can fail recovery, because their standard fields no longer match what the embedded native document projects to. `allow_legacy_relationships=True` recovers only a CycloneDX export with the exact historical edge projection, every relationship in `dependsOn` and no `conditional` flag, and still checks the coverage composition. Regenerate other exports from the native AIBOM or by rescanning; see [fingerprint migration](docs/fingerprint-migration.md).
- **MCP server source forms.** Python servers are collected only when `FastMCP` is imported by name from `mcp.server.fastmcp` or `fastmcp`, or `MCPServer` from `mcp.server.mcpserver`; `from mcp.server import Server` is reported as a gap. Other forms, such as `from mcp.server import FastMCP`, `from mcp.server.fastmcp.server import FastMCP` and the low-level `from mcp.server.lowlevel import Server`, are neither collected nor reported as a gap. Among TypeScript and JavaScript servers, only `.ts` files with a named `McpServer` import are collected; JavaScript servers (`.js`, `.mjs`, `.cjs`), namespace imports (`import * as sdk`), `require` and `.mts` or `.cts` files are skipped without a gap. Server source under directories named `build`, `dist`, `test` or `tests` (and `__tests__` for TypeScript) is skipped without a gap. Servers declared in other IDEs' MCP configuration files are not inventoried: `.vscode/mcp.json` is not read, and `.windsurf/mcp.json` and `.cline/mcp.json` are checked for valid JSON and listed by path only when a Windsurf or Cline marker file such as `.windsurfrules` or `.clinerules` exists, so a changed endpoint there raises no alert.
- **Registry manifests.** The `registry` collector reads the root manifests by pip 26.3's and BuildKit's parsing rules, but runs neither and fetches nothing. An include, constraints file or editable install that reaches beyond the root `requirements*.txt` files or the project itself, and a URL, VCS, archive or path requirement without a package name, other than the project itself, is a coverage gap. A `name @ URL` requirement, including a VCS or `file:` URL outside the project, is inventory recorded by its name and URL origin (a URL without `//`, such as `file:../pkg`, is recorded as written), with no gap unless pip could read its text as a path in the project; a bare archive that starts with an AI package name is also recorded, under a mangled name (`openai-1.0.0.tar.gz` becomes `openai-1-0-0-tar-gz`), and a bare path such as `torch/` is recorded under its name with a collection failure (`invalid or unsupported PyPI requirement`). These are not reported:
  - images named outside `FROM`, such as `COPY --from=<image>` or `RUN --mount=...,from=<image>`;
  - options that follow a requirement on the same line, other than `-e`, and `${NAME}` variables inside them (a bare `${NAME}` word after a requirement makes the line an invalid requirement, which is a collection failure);
  - a `${NAME}` variable inside a `name @ URL` reference, which is neither resolved nor reported: the reference is recorded by its URL origin, so a variable in the user information, path or query is dropped with them, one in the host is kept literally, and a URL without `//` is kept as written;
  - a `${NAME}` variable inside an option's value, such as `--index-url https://${TOKEN}@host/simple`. pip expands variables before it splits a line, so a value containing spaces could add options, including an include;
  - index and source choices (`--index-url`, `--extra-index-url`, `--find-links`, and Poetry primary or supplemental sources); those packages are recorded as PyPI packages;
  - dependencies declared only in `setup.py` or `setup.cfg`, or declared dynamic. A line that installs the project itself (`.`, `./`, `.[extras]`, `file:.` or `-e .`) is taken as covered by its `pyproject.toml`, and pip resolves such a path from the directory it runs in, which the collector takes to be the project root;
  - a `# syntax=` directive that selects another Dockerfile frontend;
  - anything in a compose file beyond the first word after `FROM` or `image:`.
- **A2A values without a binding key.** A2A records export URLs only as origins: a network-path URL (`//host/...`), or a bare `host:port` address with a dotted, `localhost` or bracketed-IP host, as `//host:port`, and other scheme-less URLs, such as `svc:50051` or `host/path`, as `[redacted]`. The OAuth and OpenID Connect scopes that a card or its skills require are exported in clear. Requirement values of other scheme types, and of schemes the card does not declare, are not exported; the unkeyed structure digest covers them, on the card and on each skill, so changing one raises a medium alert, but anyone holding the BOM can confirm a guess of them, including a credential pasted there by mistake.
  - Without `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY`, the following changes are detected only when they change a URL's shape (path depth, or whether a query, fragment or user information is present) or add or remove a top-level field of the card or client entry; fields inside skills, interfaces and security schemes are not covered, except the requirement lists, scheme types (for A2A 1.0, the scheme member) and URL fields (any field whose name ends in `url` or `uri`), where adding, removing or re-hosting one raises a medium alert:
    - a path or query change on the same host for a card's `url`, a `supportedInterfaces` or `additionalInterfaces` URL, a security scheme URL such as `tokenUrl`, or a client's `agentCardUrl` (a swap between `/.well-known/agent.json` and `/.well-known/agent-card.json` is detected);
    - any change to a URL whose origin cannot be exported, such as one without a host or with an invalid port, which is exported as `[redacted]`;
    - a changed A2A 1.0 interface `tenant`;
    - a changed scope that was redacted because it held user information, a query, a fragment, a credential assignment or a known token format;
    - values the inventory neither exports nor digests: security scheme fields other than types and URLs (such as an authorization code flow's `pkceRequired`, an API key's `name` and location, or an HTTP scheme's `scheme` and `bearerFormat`), `preferredTransport`, `protocolBinding`, `protocolVersion`, interface transports, descriptions, skill descriptions, tags, examples and input or output modes, and the id of a skill that has a name.
  - Records with an unbound URL, a tenant or a redacted scope carry a low `completeness` risk that names the key; it does not list the values the inventory neither exports nor digests. It is a risk, not a coverage gap, so gates on coverage do not fail on it, and the default risk gate, which fails only on critical findings, passes it; a risk gate set to fail on low severity fails on it.
  - A token endpoint or interface moved to another host raises at most a medium `properties changed` alert. It raises none when other URLs of that kind in the card already use the new host and still use the old one, or when the URL is exported as `[redacted]`. Supported interfaces are compared in order, and for an A2A 1.0 card without `url`, a change of the first entry's origin raises a high `endpoint_url changed` alert.
  - Scopes are read from the `security` and `securityRequirements` lists of the card and of its skills, not from `securitySchemes` flows. The specifications do not say how a skill's requirements combine with the card's, so skill requirements can make `authentication_required` false (a skill alternative that is empty or names an undeclared or untyped scheme) but never true: a card whose only requirements are on its skills is recorded as declaring none. A card that declares requirements in another form, or names a scheme that states no type (for A2A 1.0, no known scheme member), is recorded as declaring no authentication requirement.
  - Only the card's `url` and its first `supportedInterfaces` entry get the HTTPS check. A gRPC address in the `host:port` form that A2A 1.0 prescribes fails that check, because it does not show TLS.
  - A URL with a backslash before `@`, such as `https://evil.example\@good.example/`, is exported as `https://good.example` although WHATWG parsers connect to `evil.example`; its user-information shape raises only a medium alert.
  - The structure digests are unkeyed, so anyone holding the BOM can confirm guesses of field names, security scheme names, URL path depth and whether user information or a query is present.
- **ShadowScan producer verification is opt-in and not recorded.** Unless an operator signature policy names the discovery report, or the project policy sets `validate.require_discovery_signature`, `validate` and `risk` accept unsigned ShadowScan evidence. The result of the check is not written into the BOM, so `validate` or `risk` without `--project` cannot enforce it, and a project-policy setting can be removed by the change it gates. `verify-discovery --bundle` checks only a BOM written by `import-shadowscan`; for a merged `scan` BOM, use the signature policy with `--project`. A passing check authenticates the report's producer only. It does not bind the report to this repository, commit or time: anyone who can write to the checkout can substitute an older report, or another repository's report signed by the same identity, and regenerate the BOM from it. Give each repository's discovery workflow its own signer identity.
- **ShadowScan reruns need keyed credential identities.** When a report records `collection_scope.credential_identity_scope` as `run`, ShadowScan derived each redacted credential finding's id from a random per-run key. Those findings get new ids on every run, and `diff` reports them as removed and added components. Set `SHADOWSCAN_IDENTITY_KEY` for every ShadowScan run before you compare reruns.
- **Resource use on hostile input.** A TypeScript MCP server file with deeply nested constructor calls, or root `.ts` and `.js` files filled with unterminated `/*` comments, can make one scan run for minutes to hours. The scan does not pass in that time, but it can hold a CI job until the job times out, so set a timeout such as `timeout-minutes` in GitHub Actions.
- **Malformed input stops some exports with a traceback.** JSON-escaped lone surrogates (such as `\ud800`) in `rag_config.json`, A2A agent cards or `package.json` make CycloneDX, SPDX and SARIF export exit 1 with a Python traceback (for an A2A card only when the value is in a field the record carries, such as the card's or a skill's name; a value in a requirement list or in the name of a skill with requirements is instead a scan failure, as is any such value when collected with `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY`, and one in a field the record does not carry, such as `description`, exports cleanly), and the native JSON written for such input is refused by the other commands. MCP tool input schemas nested a few hundred levels deep make `scan` exit 1 the same way. Both fail closed.
- **GitHub Action.** The Action uploads evidence under the fixed artifact name `nexus-symbiote-aibom` and SARIF under the fixed category `nexus_symbiote`. Run it once per workflow run: a second scan in the same run fails to upload its artifact, and a later SARIF upload for the same commit replaces the earlier one. An earlier step in the same job that runs untrusted code can change the runner's Python or rewrite files under `RUNNER_TEMP` before the Action reads them, so write the signer policy from a trusted source and run untrusted build or test steps in a separate job.
- **Sigstore trust root.** Offline signature verification by the CLI uses the trusted root that sigstore-python caches in your user cache directory: `$XDG_CACHE_HOME/sigstore-python` whenever `XDG_CACHE_HOME` is set, on Linux and, with the pinned platformdirs, also on macOS; otherwise `~/.cache/sigstore-python` on Linux or `~/Library/Caches/sigstore-python` on macOS. Offline, sigstore-python reads that file without verifying it, so anyone who can write there chooses which certificate authorities and transparency logs are accepted. The GitHub Action gives its scans an empty private cache, so it always uses the root embedded in its hash-locked `sigstore` package. That root ages: a bundle that relies on a key Sigstore introduced after that release fails verification until you update the Action pin. On shared or persistent machines, such as self-hosted runners, run the CLI with `XDG_CACHE_HOME` set to an empty directory you own, on Linux and macOS alike; on macOS, setting `HOME` alone is not enough when `XDG_CACHE_HOME` is set.
