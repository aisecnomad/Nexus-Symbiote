# Security model

Nexus SymBiote connects an agent's inventory to evidence and policy. Keep the following states separate:

| State | Meaning |
| --- | --- |
| Declared composition | A repository, supplier, or configuration says a component is used. |
| Observed composition | A named collector measured a component in a stated scope and time. |
| Approved configuration | An authorized approver accepted a specific configuration and capabilities. |
| Mediated execution | An enforcement adapter checked an actual action against its trusted policy and approval. |

A component's `assurance_level` describes its identity: `observed` when a collector computed it from bytes (a weight, instruction, skill or tool-descriptor digest), `declared` for a configuration, manifest, package pin or supplier statement. Each locally collected component also carries a `repository_presence` claim naming the collector that observed it.

Nexus-ShadowScan is the primary discovery source; importing its report into Nexus SymBiote preserves the distinction between a supplied claim and a new local measurement. A2A Agent Cards, IDE configuration, and extension manifests are declarations until their relevant identity and evidence are separately verified.

An inventory entry never grants permission by itself. A schema hash pins an interface; it does not constrain a backend's hidden side effects. A signed malicious artifact remains malicious. Runtime metadata emitted by the agent itself has a different trust basis from an independent observation.

Collectors must preserve coverage limitations, denied reads, unsupported inputs, exclusions, and failures. Some unsupported inputs are still skipped without a gap; the [known limitations](known-limitations.md) list them. Missing information means unknown, not verified absence. Secrets are references, not values. Avoid default capture of raw prompts, retrieved documents, tool arguments, or results. Tenant and deployment identifiers must remain part of approval and observation scope.

## Design principles

1. **Never runs what it inspects.** Collection is static. It does not execute project modules, model loaders, repository hooks or MCP launch commands.
2. **Offline by default, enforced at run time.** Every command runs under a tripwire that makes this package and its dependencies fail closed on name resolution, network connections and process creation unless you opt into live mode for one of three commands. It is not a sandbox; add an operating-system network boundary where one is required.
3. **Unknown is not safe.** Failed reads, skipped collectors and the unsupported declarations a collector recognizes are recorded as gaps, and default gates fail on them instead of passing silently. Surfaces the collectors do not support are not recorded at all; the [known limitations](known-limitations.md) list them.
4. **Claims are not evidence.** Declared, observed, approved and mediated states stay separate. A supplier label or an adjacent signature file never upgrades trust by itself, and `--no-project-policy` stops an untrusted checkout from choosing its own gates.
5. **Standards first.** One native inventory exports to CycloneDX 1.7, SPDX 3.0.1, SARIF 2.1.0 and VEX. CycloneDX and SPDX carry the full native inventory in a digest-bound extension; retain it to recover native semantics. SARIF and VEX project findings and do not carry the full inventory.

When a supplier gives you an inventory and you have the corresponding checkout,
use both commands against the same project root.

```sh
nexus-symbiote validate inventory.json --project /reviewed/checkout --no-project-policy
nexus-symbiote risk inventory.json --project /reviewed/checkout --no-project-policy --json-output
```

Project reconciliation reruns the supported static collectors and compares
their security-relevant fields and findings with the supplied BOM, together with
the repository agent's profile and references and every relationship between
locally collected components. It needs at least one local subject. A supplied
component or relationship the checkout cannot corroborate fails reconciliation
when it claims local provenance, verified assurance or internal-verified trust;
otherwise it is listed as a supplier claim and the basis becomes
`project-reconciled-with-supplier-claims`. A claim the supplier adds to a locally
collected component, including one in place of a claim the collector could not
make, is listed the same way and fails when it asserts verified assurance. Such a
claim never counts toward `validate.minimum_assurance_level: observed`: a component
that only supplier additions show as observed is judged as declared. A supplier
cannot add a `hashes` entry the collector did not record, or a collector-owned
property (`collection_mode`, `content_hash_withheld`, `identity_source`,
`weight_files`, `config_hash`, or any `static_value_binding*`,
`static_config_hash*` or `static_card_hash*` key): integrity, suppression
fingerprints and the static binding checks read them as collected evidence, so
reconciliation fails instead. `trifecta` and `diff` read saved inventories,
so their conclusions depend on the provenance of those files.
A mismatch makes `validate` report the basis `project-reconciliation-failed` and
makes the project-backed risk command exit unsuccessfully with that basis, an
unknown risk level and a null score. Without a project, `risk` scores the supplied claims
and labels the result `supplied-bom`. For an operator-configured signature
check, supply the trusted signer policy when validating the project. In the
GitHub Action, pass it with the `signature-policy` input as a caller-owned file
outside the workspace; the Action verifies against the Sigstore trust root
embedded in its hash-locked runtime, not a runner cache.

A mediated action needs a trusted approver, snapshot binding, authenticated workload and endpoint, action/resource constraints, validity, current revocation state, rollback protection, and any action-specific approval. One-use approval must bind to the action and arguments it authorizes. Adapter checks cannot govern tools invoked through an unmediated route; deployments need their own network, identity, and sandbox controls to make mediation complete.

For hosted models, an alias is a locator. Provider-reported revisions and behavioral canaries do not establish measured weight identity. Preserve identity assurance and unknowns explicitly. For retrieval and memory, record the source and index versions, effective reader/writer permissions, and derived records requiring invalidation after withdrawal.

## Known false-positive and false-negative classes

These are current behaviors, not guarantees. Review them before relying on a gate. They explain how findings are classified; what the collectors do not record or verify is in the [known limitations](known-limitations.md).

- **Model format by extension.** `.pkl`, `.pickle`, `.pck`, `.dill`, `.cloudpickle`, `.pt`, `.pth`, `.bin`, `.joblib`, `.ckpt` and `.pdparams`, also inside one or two archive or compression suffixes (`.tar`, `.gz`, `.bz2`, `.xz`, `.lzma`, `.zst`, `.z`, `.lz4`, `.zip`) such as `.pth.tar`, `.pkl.gz`, joblib's `.joblib.z` or pandas' `.pkl.tar.gz`, are rated by their inspected content, not by the name alone: a recognized pickle opcode stream, a NumPy object-dtype array, or a ZIP archive, such as a torch archive, with a pickle-family member or such an array as a member, is critical with that evidence, and a file whose first 64 KiB show none of that, such as a zero-filled or firmware `.bin`, is unknown (`Named pickle-family format; no pickle evidence in the inspected prefix`; `empty file` for a zero-length one), a high finding that the default gate does not fail on by severity alone. A pickle-family file that cannot be read keeps the critical rating. A pickle opcode stream that a bound cuts short before a recognized shape or a call, a ZIP archive whose directory is over 1 MiB or malformed or with a member that was not checked, and a NumPy header over 64 KiB are pickle evidence under such a name, so they stay critical, with the bounded verdict as evidence; so is a compressed or archived stream, by a wrapper suffix, by its compression magic, by an LZMA-alone header after joblib's `5d 00`, by the ustar magic or by a tar header that `tarfile` reads without it, whose decompressed content is not inspected, and so is a file that starts with the GGUF magic, whatever follows, as llama.cpp opens a model by its magic and the chat-template check runs only under a `.gguf` name. Formats with no structural validator (`.onnx`, `.gguf`, `.ggml`, `.h5`, `.hdf5`, `.keras`, `.tflite`, `.mlmodel`, `.pte` and TensorFlow's `saved_model.pb`) are reported as unknown, not safe, unless their content is a recognized pickle, a NumPy object-dtype array, or a ZIP archive, such as a torch archive, with a pickle-family member or such an array as a member, or a GGUF chat template matches the potential Python-internals access heuristic; a configured template that matches adds a critical finding and leaves the rating unknown. A match does not establish execution or a sandbox escape, and the heuristic can miss computed names. A record's format and model type also come from the file name, except under `.gguf` and `.safetensors`: a file there without the GGUF magic or a SafeTensors header that validates stays a component, rated as its content is, without a format or model type ([format and model type](model-integrity.md#format-and-model-type)). A file outside these lists is still inventoried by its content when it is named `.npy`, `.npz` or `.dat` or has any name under a `model`, `models`, `weights`, `checkpoint` or `checkpoints` directory: that same content is critical, and a NumPy header or ZIP archive that the inspection bounds left unread is unknown. Other files outside the lists are not inventoried ([known limitations](known-limitations.md#models)). See [model integrity](model-integrity.md).
- **Risk score scale.** The aggregate score is the uncapped sum of finding weights (critical 10, high 7, medium 4, low 1, info 0). It grows with inventory size and is not a percentage. `risk --json-output` records that as `gate.score_scale` = `unbounded-sum`. The Action's `risk-threshold` input still accepts only 0 to 100, which is a threshold for that sum, not a bound on it. Low findings add up too: without `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY`, each record with unbound values adds 1 ([known limitations](known-limitations.md#mcp-servers-and-tools)). The built-in CLI policy fails on any critical finding regardless of the aggregate. The Action's `fail-on-severity` input defaults to `high`, so high findings fail an Action run on their own. The Action's `risk-threshold: '0'`, like `risk --no-score-threshold`, removes only the score threshold: findings at or above `fail-on-severity`, unverified SafeTensors, incomplete coverage and missing evidence still fail the gate. The [finding catalog](finding-catalog.md) lists every category with its severity.
- **Free-text redaction.** Every rule below and every known value is matched in the original text, the rules also in the text with each known value masked, and each union of their matches is replaced by one marker, so a known value cannot erase the name, scheme or header a rule reads, nor glue itself to a token, scheme or header name the rule must see start or end. A crafted set of values that are all parts of one another, repeated in a text, is covered by its greedy replacement widened by the longest value, which can also hide characters next to it. Redaction removes known secret values, every occurrence including overlapping ones; `name=value` and `name: value` pairs, with the name optionally quoted and the value up to whitespace, `,` or `;` or a whole quoted string, in which a backslash escapes the next character, whose name contains `api_key`, `access_key`, `secret_key`, `private_key`, `account_key`, `token`, `password`, `passwd`, `passphrase`, `pwd`, `secret`, `credential` or `sig`, or 2 to 24 letters or digits followed by `_key` or `-key` (`encryption_key=`, `signing-key:`, which also hides the values of names such as `primary_key` and `public_key`), directly or followed by digits or by up to four `-`, `_` or `.` delimited parts (`DB_PASSWORD_PROD=`, `token2=`), but not followed by letters (`max_tokens=`, `tokenizer=`); the credential after `Bearer`, `Token`, `Bot`, `ApiKey` or `Api-Key` when it has at least 16 characters, or at least six with a digit, punctuation, or both lower- and upper-case letters with an upper-case one after the first character (prose such as `Bearer authentication` survives), and after `Basic` when it decodes to a `user:password` pair; whatever its shape, the value after any of these schemes, or after `Negotiate` or `NTLM`, when it follows an `Authorization` or `Proxy-Authorization` header name (`Authorization: Basic ...`, `"Authorization": "Bearer ...`, `authorization=Token ...`, `Authorization: Negotiate ...`); PEM private key blocks; and tokens in known formats (JWTs and `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `glpat-`, `xox`, `sk-`, Stripe live and test keys, `AKIA`, `ASIA`, `AIza`, `ya29.`, `npm_`, `pypi-`, `hf_`, `pcsk_`, `gsk_`, `r8_`, `pplx-`, `xai-`, `lsv2_pt_`, `lsv2_sk_`, `tvly-`, `fw_` and `dckr_pat_` prefixes, the last ten only before a body of at least 20 characters, so model and module names such as `pplx-7b-online` or `fw_config_loader` survive; SendGrid keys (`SG.` and two dot-separated parts of at least 16 characters each), Shopify tokens (`shpat_`, `shpss_`, `shpca_` or `shppa_` and 32 hexadecimal digits), Twilio key SIDs (`SK` and 32 lower-case hexadecimal digits), Databricks tokens (`dapi` and 32 lower-case hexadecimal digits), Slack app-level tokens (`xapp-` and at least 20 characters), Postman keys (`PMAK-`) and Doppler tokens (`dp.pt.`, `dp.ct.`, `dp.st.`, `dp.sa.`, `dp.scim.`, `dp.audit.`, or `dp.st.` and a config name of 2 to 35 lower-case letters, digits, `_` or `-`, then at least 40 letters and digits)), which all but JWTs and `sk-` keys are also found after `_` or `-` inside a name (`AWS_AKIA...`, `X_glpat-...`). Names compared with live evidence, such as server and tool names, get only the URL, assignment and scheme rules and those in-name token formats, so `sk-learn-classifier` stays a name. Credentials in other shapes are not recognized by pattern. MCP configuration scrubs the environment, header and launcher values of every server declared in the same file from each server's free text and tool lists only when the variable, header or option name marks a credential (it contains `KEY`, `TOKEN`, `SECRET`, `PASS`, `PWD`, `CREDENTIAL`, `AUTH`, `COOKIE`, `SESSION`, `PRIVATE`, `SIGNATURE`, `CERT`, `DSN`, `JWT`, `BEARER`, `HEADER`, `PAT` as a word, or a connection-string name) or the value has a known token format, authentication scheme credential or URL user information, and the value has at least eight characters. Launcher values are the `NAME=value`, `--name=value` and `--name value` arguments, base64 padding included, also as words of an inline shell or `cmd` script; a requirement such as `pkg==1.2` or `pkg>=1.2` is not an assignment, a `${NAME}` or `$NAME` reference is not a value, and a `--header` or `-H` value is read by its own header name. Every string of at least eight characters in an `oauth` or `auth` object counts under any key, as that field name marks a credential, except a plain URL, a reference, and the OAuth parameters sent in clear (`type`, client id, scopes, audiences, resource, grant and response type, redirect URI and issuer) unless their shape marks them; an object of more than 20,000 nodes or 64 levels is a scan failure, not read in part. In a URL in any of these values or in an endpoint field, the password counts on its own when it reads as a credential by the rule for scheme values (at least 16 characters, or a digit, punctuation or both cases), and so do the values of query parameters whose name marks a credential; a user name without a password counts only in a known token format, and a password that reads as a word, such as the default `postgres`, is scrubbed only within its whole value ([known limitations](known-limitations.md#mcp-servers-and-tools)); when such a value is an authentication scheme word, whitespace and a credential (`Bearer <token>`, `Basic <base64>`), the credential of at least eight characters is scrubbed on its own as well, so a tool name or text that repeats the bare token is redacted; such a value that occurs in a server name, tool name, command, package reference, package source or endpoint origin withholds that field and is a coverage gap, and a launcher package whose name or specifier is in a known token format is withheld the same way, as a token-shaped command is. RAG identifier fields (`type`, `store_type`, the embedding model, the chunking strategy and the index identities) are exported only when the identifier rules leave them unchanged and they hold no `:`, the shape of `user:password` and `host:port`; a `source_uris` entry is exported as written only when it is a plain path holding a `/` or a `.`, so a bare token is exported as `[redacted]`. In free text a URL ends at whitespace, a quote or an angle bracket; `scheme://` URLs keep only their scheme, host and port unless another match reaches into them, and one without a host, or whose authority holds a backslash, which browsers read as the end of the host, is replaced entirely. A dependency declared as a direct URL or VCS reference is redacted from the URL its requirement parses to, so it is recorded without its path, revision or query, and a change within the same origin (scheme, host and port) does not show in `diff`. A reference written without `//`, such as `file:/path`, or a relative path is recorded as written.
- **Hard links.** A hard-linked file inside the scanned root is collected like any other regular file and no failure is recorded: confinement is descriptor-relative and follows only a relative symlink to a regular file or directory in the project other than its root, resolved lexically without another symlink, but it does not establish inode provenance. A refusal would also fail legitimate deduplicated trees (`uv` and conda environments, Nix and Guix stores, `cp -al` mirrors). The [security boundaries](../SECURITY.md#security-boundaries) say how to run collection safely.
- **Hosted CI.** A configured workflow is not evidence that it ran; see `docs/repository-controls.md`.
- **Hidden characters.** The `prompt` collector reports every format character (Unicode category Cf), variation selector and blank filler, such as U+180E and U+3164, and every code point that Unicode reserves as default-ignorable without assigning it (U+2065, U+FFF0 to U+FFF8, U+E0080 to U+E00FF and U+E01F0 to U+E0FFF): bidi embeddings, overrides and isolates, tag characters and those unassigned code points of plane 14 as critical, the directional marks LRM, RLM and ALM as medium, and the others as high. The `mcp` collector rates the text of each tool definition in a `tools` array the same way. A zero-width joiner between pictographs, a presentation selector (U+FE0E or U+FE0F) after a pictograph, a keycap base or another character that Unicode's emoji variation sequences give one (such as `‼`, `™`, `Ⓜ`, `〰` or `㊗`), but not after other characters such as a space, a dash or kana, the England, Scotland and Wales flag sequences and a byte-order mark that starts the text are not reported; pictographs are recognized by code-point ranges. Ordinary text can therefore raise findings: right-to-left text uses directional marks, a medium finding, and the joiners and variation selectors that Persian, Indic or Mongolian text uses are high findings. HTML and Markdown comments are a `hidden_markup` finding, reported by count, in Markdown files and in instruction files without a suffix. HTML comments include the processing instructions (`<?...?>`), declarations (`<!X...>`) and CDATA sections (`<![CDATA[...]]>`) outside code, which HTML parsers read as comments, and in HTML blocks also `<! ...>`, `<!-...>`, `</ ...>` and `</3...>`. A Markdown comment is a link reference definition, whatever its label, destination or title (`[note]: # (...)`, `[COMMENT]: <> (...)`, `[//]: https://example.com (...)`), that no link in the file uses, every later definition of a label already defined, a definition with a `#` or `<>` destination wherever it is outside code, used or not, and a footnote (`[^x]: ...`) that nothing references, which GitHub drops with its continuation lines, its indented paragraphs and the lines right after them that start no block: a definition is visible only as the destination of the links that use it. A reference counts as a use only where every CommonMark reader makes a link of it whose text shows more than spaces and punctuation, so not in code, raw HTML, an autolink, a URL that GitHub makes an autolink of (`https://docs.example/[note]`) or a link destination, and not `[][note]`. Each comment is rated by its whole text, a title or footnote across lines included: high when it holds a URL, a path under `~/`, an instruction word such as ignore, execute, download or install, or `run` followed by a path, a script or executable file name, a shell (`run /bin/sh`, `run deploy.sh`, `run bash`) or a command that executes code, reads secrets or deletes files (`python`, `python3`, `py`, `node`, `deno`, `bun`, `ruby`, `perl`, `php`, `java`, `osascript`, `npx`, `uvx`, `pipx`, `pip`, `pip3`, `npm`, `pnpm`, `yarn`, `uv`, `poetry`, `cargo`, `go`, `brew`, `apt`, `apt-get`, `gem`, `sudo`, `doas`, `su`, `env`, `exec`, `eval`, `source`, `curl`, `wget`, `iwr`, `cat`, `cp`, `mv`, `rm`, `dd`, `chmod`, `chown`, `ssh`, `scp`, `nc`, `base64`, `xargs`, `docker`, `kubectl`, `git`, or the PowerShell `iex`, `irm`, `Invoke-Expression`, `Invoke-RestMethod` and `Invoke-WebRequest`; `run python x.py`, `run cat .env`, `run rm -rf /`, but not `run go-live`), also after punctuation or markup such as `:`, quotes, `(`, `[`, `**`, `<code>` or a code fence and its language (`Run: ./setup.sh`, `run (bash)`), otherwise low, so `Run make docs`, `dry-run` and `last run:` stay low. A hyphen joined to a word before `run` makes a noun, except in `re-run`. `run` followed by `this`, `these`, `it` or `the following` is high when a path, a script or executable file name, a shell or one of those commands appears later in the same comment (`run the following command: ./evil.sh`, `run this: /tmp/x`). `run` is also high when one of those starts a command later in the same sentence: at the start of a line or list item (`-`, `*`, `+`, `1.`, `1)`), or after `:`, `;`, `&`, `|`, `then`, `command`, `commands` or `script`, with only whitespace, quotes, brackets, `*`, `_`, `>`, `-` or `$` between (`` run the command `rm -rf /` ``, `run the setup script: python setup.py`, `run as root: rm -rf /`, `run make test && rm -rf /`, `run tests, then cat .env`, `run:` followed by a code block or a numbered list item). The abbreviations `e.g.` and `i.e.` introduce a command target directly after `run`. An intervening phrase such as `run the suite, e.g. python tools` stays low. A sentence ends at `.`, `!` or `?` before whitespace, except after a digit or in either abbreviation. The matcher reads a whole path or variable as a single target even when its name contains another verb. Otherwise `run` before another word stays low, as in `run make test`, `run the linter`, `run them with python`, `Run make docs. Note: python 3.11 is required` or `test run`. The high rating is by shape, so a note such as `<!-- see https://example.com/style -->` rates high, and so does a definition with a URL that no link uses, such as one left after its badge was removed; with the Action's default `fail-on-severity: high` either fails a default run, so move notes out of agent instruction files and remove unused definitions. Being by shape, it also rates an instruction in other words low, such as `<!-- always answer in French -->`; see [known limitations](known-limitations.md#instructions-and-ide-settings).
- **Hook commands.** A hook command is rated from its text; it is not run. It is critical when any earlier segment of a pipeline downloads (`curl`, `wget`, `iwr`, `irm`, `Invoke-WebRequest`, `Invoke-RestMethod`) or runs `base64 -d` or `base64 --decode`, and any later segment is a shell (`sh`, `bash`, `zsh`, `dash`, `ksh`, `ash`, `fish`, `pwsh` or `powershell`), named alone, by a path that ends in the shell or through `env`, including an assignment such as `env FOO=1 bash` and `env -i`. A newline after `|` or `|&` does not end the pipeline. Quotes and backslash escapes are removed first (`'sh'`, `s\h`, `c\url`), and `${IFS}` or `$IFS` counts both as an empty insertion (`c${IFS}url` reads as `curl`) and as a split (`bash${IFS}/dev/stdin` reads as `bash`). `sudo`, `command`, `exec`, `busybox` and a group (`(sh)`, `{ sh; }`) may stand in front of the shell. `command -v` does not run it. `sh < <(curl ...)`, a short flag ending in `c` such as `bash -lc "$(curl ...)"`, and a here-string `bash <<< $(curl ...)` are the same substitution. `iwr` or `irm` piped to `iex` is critical, as is a download piped to `python`, `python2`, `python3` or `py` with no script file (`python3 -`) or to `perl` with no `-e` program. Saving the download (`curl -o`, `curl --output`, `wget -O`, `iwr -OutFile`) and later running that file (`bash a`, `./a`) is critical. A literal URL is not required, so `curl $URL`, `curl ${URL}` and `curl "$URL"` are the same shape as a command that contains `https://`. `|&` is a pipe and `||` is not. It is also critical when one of those shells, or `eval`, `source` or `.`, runs a command substitution, a process substitution or backticks whose command is one of those downloads or decodes (`sh -c "$(curl $URL)"`, `bash <(curl $URL)`, `eval "$(curl $URL)"`, `` `curl $URL` ``, `source <(curl $URL)`), or when PowerShell receives `-e`, `-ec` or a prefix of `-EncodedCommand` (`-en`, `-enc`, `-encoded`, `-EncodedCommand`), all of which its console host reads as that parameter, among its own parameters, after `-`, an en dash, an em dash or a horizontal bar, quoted or not. `-ex` and `-ep` are `-ExecutionPolicy`, not that parameter. A shell name followed by an expansion, as in `bash${IFS}/dev/stdin`, counts, because the expansion may split the word. A `powershell` or `pwsh` name counts wherever it appears in a segment delimited by `;`, `&`, `|` or a newline, so a wrapper such as `cmd /c`, `start`, `sudo` or `Start-Process powershell -ArgumentList '...'` keeps the command critical; in a plain argument it counts only as the last path component, so `tools/pwsh/lint.ps1` is not PowerShell. Its parameters end at `-Command`, `-CommandWithArgs`, `-File <script>` or the first argument that is not a parameter's value, because PowerShell passes the rest to the script or command; `-File -` reads commands from standard input and does not end them. `-NoProfile`, `-NoLogo`, `-NonInteractive`, `-NoExit`, `-STA` and `-MTA` take no value; the argument after any other parameter is read both as its value and as the next parameter, and the hook is critical if either reading reaches an encoded command. Only a plain argument, made of letters, digits, `_`, `.`, `+`, `:`, `=`, `#`, `~`, `/` and dashes with a `\` only between them, ends the parameters. The shell may rewrite any other argument, such as a redirection, an expansion, a quoted value or an escape (`2>/dev/null`, `$FLAGS`, `-wd "C:\Program Files"`, `"-NoProfile"`, `^-nop`), so after one every later encoded flag in the segment counts, and `pwsh "$SCRIPT" -enc SQBFAFgA` and `grep -rn pwsh "src dir" -enc SQBFAFgA` rate critical. A bare `-e` after one does not (`pwsh "$SCRIPT" -e dev`). After `-File`, a quoted or expanded script path that contains `/`, `\` or `.`, such as `"$CLAUDE_PROJECT_DIR/check.ps1"`, still ends them. A PowerShell name that is the value of another command's option and is followed by an encoded prefix still rates critical, as in `grep -e pwsh -enc SQBFAFgA` or `winget install --id Microsoft.PowerShell -enc SQBFAFgA`, and so do the same commands with a bare `-e`: a false positive accepted because `-e` is PowerShell's shortest encoded-command flag. Not rated critical: `command -v`, an interpreter given a script file (`python3 script.py`, `perl script.pl`, `perl -e`), a saved download run under a different name (`curl -o a ... && bash other`), an `-e` after a script (`pwsh -File build.ps1 -e dev`), `/enc` and `--enc`. A command that contains a URL and is not one of the shapes above is high, and anything else is medium.
- **Unsupported surfaces.** A surface no collector reads is not a coverage gap, so gates pass and `diff` reports no change when it changes. A value the inventory binds only with `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY` is not named in an alert without the key. For a record that carries a low `completeness` risk saying its values are not bound in this inventory, such as an MCP server's launch values, IDE agent settings values, A2A and RAG URL paths and inline RAG documents, or a prompt file whose content hash is withheld, with or without that risk, such as an `@path` import that is not Markdown or a prompt template (templates share one such risk), `diff` instead reports a medium alert on every comparison, changed or not, that the values are unbound, so a widened argument or a same-host path change cannot pass `--fail-on-alert` silently. A value only the key binds on a record without that risk, such as an A2A skill description, still raises no alert without the key. The [known limitations](known-limitations.md) list both, and which records then carry the `completeness` risk that names the key.

## What results do and do not establish

A successful scan is an inventory result. It does not establish that a model is benign, that a tool backend obeys its description, or that every agent action was mediated. Inspect the exit status and the inventory's coverage, exclusions and failures: a command may write evidence and still return a failing gate, and exit code `0` for informational commands, report-only output and skipped gates does not establish approval.

Collection is static by default and does not execute project modules, model loaders, hooks or MCP launch commands. A completed search can find no matching files. Failed reads and the unsupported declarations a collector recognizes remain coverage gaps, but some declaration forms and file types are skipped without a gap (see the [known limitations](known-limitations.md)), and collectors omitted from `--scanner` remain unknown. The `registry` collector reads every `requirements*.txt` in the project root, matching names without regard to case (a name with undecodable bytes or a control or format character is reported as a gap and not read), by pip 26.3's parsing rules, and does not follow includes, constraints files, editable installs or the targets of URL, VCS and path references. Each of these is a coverage gap or failure: an include, constraints file or editable install that reaches beyond the root requirements files or the project itself; a requirement that pip installs from a URL, VCS reference, archive or local path instead of by a package name, other than the project itself, or a `name @ URL` line whose text, read as a path, leaves the project root or starts with one of its entries (other `name @ URL` lines are recorded under their name and URL origin without a gap); an option pip 26.3 does not know on an option line; a `${NAME}` variable in a requirement's name or in an option line's option place (options after a requirement, other than `-e`, are not checked); and a declared encoding other than UTF-8. pip expands `${NAME}` variables before it splits a line, so a variable inside an option's value is not resolved or reported, and a value containing spaces could add options, including an include. A named `name @ URL` reference is recorded with its URL origin only, or as written when the URL has no `//`; a line that cannot be parsed is recorded only up to the word that holds its first `//`. A bare archive or directory path that starts with an AI package name is still also parsed as a requirement, so besides its coverage gap it can be recorded under a mangled name or reported as an invalid requirement. Dockerfile `FROM` instructions are read by BuildKit's default frontend rules, including continued lines, heredocs and build stages, and an image that BuildKit would resolve differently (an ARG substitution, quotes or escapes) is a gap. Configuration presence does not prove that a server is running or that its live tool definitions match the declaration. `verify-live` is a separate explicit execution operation requiring an independently pinned launcher policy and external isolation, and `discover-mcp` is an explicit HTTPS observation operation. Neither calls tools.

Standalone `scan` evaluates the policy in its target. `validate` and `risk` evaluate the policy in the directory supplied with `--project`. Tightening settings apply automatically, including in mixed files. Relaxations require `--accept-project-policy`. A signed operator policy bounds the result. `--no-project-policy` skips checkout policy discovery. Policy in a parent directory or beside a standalone inventory cannot govern that inventory. When a project policy is honored, `validate` names its source, `risk` records it as `policy_source` and `scan` writes it into the inventory's metadata, with every relaxation of the built-in gates, and every setting that changes reported results, listed under `policy_weakened` and, in human-readable output, warned about on stderr, so a switched-off gate is a visible choice rather than a silent one. The [policy reference](policy-reference.md) lists every setting. Standalone ShadowScan imports require a new output path and retain partial coverage; `--report-only` is an explicit inspection mode. Imported discovery remains a source claim and does not establish deployment, effective access or authorization.

Project validation compares static MCP and A2A records and configured tool fingerprints with fresh local evidence. A structure binding detects added or removed arguments, environment variables, headers, resolver settings and tools, and changed launchers, package identities, versions and pins, package source origins (including project `.npmrc`, `bunfig.toml`, `.yarnrc.yml` and `uv.toml` registries), launch context and endpoint origins. With `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY` set, a keyed binding also detects same-version package swaps and changed argument, environment, header, endpoint, index and resolver setting values, without exporting anything a secret could be guessed from. Without the key, MCP records carry a low completeness risk that names it. Tool `definition_hash` values are an exception: they are unkeyed digests of the original declared descriptor, so a low-entropy value that the exported descriptor omits can be confirmed by guessing. A2A records export OAuth scopes and URL origins in clear and carry unkeyed structure digests over top-level field names, counts, URL shapes and the requirement alternatives of each card and its skills, including the requirement values of schemes other than OAuth 2.0 and OpenID Connect, so anyone holding the BOM can confirm guesses of those values. With the key, they also carry an HMAC over the whole card or client entry, which detects same-host path, tenant and token URL changes; without it, records with unbound URLs, tenants or redacted scopes carry a low completeness risk. RAG sources carry the same pair: an unkeyed structure digest and, with the key, an HMAC over the declaration. IDE settings files carry a digest of each file's redacted form (`settings_hashes`, profile `settings_hashes_profile`), with or without the key, so no unkeyed digest covers a settings `env` value or the command of a credential helper such as `apiKeyHelper`, and, with the key, an HMAC over every file as read. A memory file's import of a file that is not Markdown, or of a name that a symlink resolves to such a file, carries no unkeyed content digest, and neither does any other instruction, rule, prompt or subagent file the `prompt` collector records whose bytes are not those of an instruction file: an instruction or nested memory file such as `AGENTS.md` that a symlink resolves to a file without a Markdown suffix, such as `config/app.json` or `config/.windsurfrules`, or a rule, prompt or subagent file such as `.cursor/rules/x.json`; the files of a skill or command directory keep their `sha256` digests. With the key, such a file carries an HMAC over its text, which project validation recomputes. The `prompt` collector does not read a file without a Markdown suffix whose name, or a directory on whose path, says it holds credentials, such as `.env` or `secrets/token.txt`, whether a memory file imports it, an instruction, rule, import or skill file is a symlink to it, or a rule, subagent or skill directory holds it, so no digest covers it ([files named as holding credentials](verification-source-binding.md#files-named-as-holding-credentials)). MCP references include the relative configuration path and declared name. Legacy snapshots without the binding, or with name-only identities, need recollection; see [source reconciliation and migration](verification-source-binding.md). Python, TypeScript and JavaScript source declarations are collected only from files that name the MCP SDK or, for Python, a supported agent framework, outside test, build, documentation, benchmark and example directories, and within the [collection limits](collection-limits.md); unresolved or dynamic registrations, constructor-supplied tools, low-level servers, decorators on imported servers, SDK imports in a parsed file that the analysis cannot follow, dynamic imports of the SDK and servers that application code starts or reaches are reported as gaps; the [known limitations](known-limitations.md#mcp-servers-and-tools) list the forms that leave none.

CycloneDX 1.7 and SPDX 3.0.1 exports use supported standard structures and a digest-bound native extension. Consumers must retain that extension to recover full native semantics and inspect the selected-field loss report. Without the extension, standard fields still guarantee two things. First, a conditional edge never appears as a typed, unconditional relationship: CycloneDX leaves it out of the dependency graph, and SPDX exports it as `other` with a `comment` that names the native relationship and states the condition. Every other SPDX `other` relationship names its native relationship in a `comment`. Second, coverage is never `complete`: the CycloneDX `compositions` aggregate and the SPDX relationship `completeness` are `incomplete` for scoped, failed, excluded or imported collection, including a claim that carries any imported-discovery field without a report digest, and otherwise `unknown` or `noAssertion`. Which collectors ran, what failed and what was excluded remain extension-only. Each export declares the projection version that produced its standard fields, and recovery rejects any standard field that disagrees with the embedded native document under that projection, apart from the exact historical edge projection that `allow_legacy_relationships` accepts for exports without a version; exports from builds before 0.1.0 may need to be regenerated, and a CycloneDX reader that drops an `incomplete` composition, as cyclonedx-python-lib does when it reserializes, leaves a document that no longer recovers. A digest detects changes; it does not authenticate the producer. SPDX identities are scoped to each inventory revision. SARIF contains reviewable findings rather than an admission decision; it marks a run with a collection failure as unsuccessful, and standalone ShadowScan imports do not support SARIF. [Standard exports](standard-exports.md) maps every field. VEX output marks findings `in_triage` and does not assert exploitability. Schema validity alone establishes neither semantic equivalence nor complete collection.

Inventories can expose infrastructure, permissions, source references and instruction fingerprints. Restrict evidence access and retention, and review artifacts before sharing them. Use independent expected digests and signer/issuer policies; a signature or registry label does not establish content safety. IDE permission records describe collected project declarations: Claude's `permissions.defaultMode`, the blanket grants in its allow list, how many allow, ask and deny rules and hook handlers it declares, findings for hooks and other risky settings, and a digest of each settings file's redacted form are retained; with `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY` an HMAC under the key also binds every value. The rules and hook commands themselves are not recorded (see the [known limitations](known-limitations.md#instructions-and-ide-settings)), and user/managed policy, workspace trust and session flags remain outside effective-authorization verification. Scanner failures emit application-owned diagnostic codes; raw exception text and invalid model configuration values are omitted from failure reports. `--debug` prints the class and code locations of a collector or internal error, never its message.

The security and inventory benchmark corpora are finite regression cases. They establish no representative field accuracy, complete collection or percentile ranking.
